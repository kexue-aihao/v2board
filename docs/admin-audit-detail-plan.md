# 后台详细安全审计评估与实现计划

评估日期：2026-10-05。状态：已按本计划实现并补齐中断的开发工作。各阶段的实际覆盖、验证结果和部署步骤见 [详细审计交付与覆盖清单](admin-audit-detail-coverage.md)。下文保留原始设计，实际实现边界以交付清单为准。

## 1. 可行性结论

可以实现。现有系统已经具备操作者身份、请求关联、模型变更采集、部分配置快照、队列关联及审计完整性校验，能够在此基础上补充业务详情，无需重建整个 4A 系统。

目标是让每项后台操作回答：谁在什么时候、通过哪个功能、对哪个对象做了什么、哪些内容从什么值变成什么值、影响了哪些关联对象、最终结果如何。查询、预览、新增、编辑、状态切换、删除、批量处理和异步任务分别记录，不能统一描述成“保存配置”或“修改资料”。

实现需要同时改动采集、业务语义、查询接口和详情页面。只增加中文接口名称，或者只把已有 JSON 展开成表格，均不能覆盖全部需求。

## 2. 现有代码为什么记录笼统

| 现状 | 代码依据 | 对详细审计的影响 |
| --- | --- | --- |
| 中文描述主要由控制器方法名称生成，再附加 ID | `app/Services/SecurityAuditDescription.php` 的 `describe()` | 不体现具体字段、前后值及业务结果；同一保存接口的新增和编辑难以区分 |
| Eloquent 事件保留脱敏前后快照 | `app/Services/SecurityAuditService.php` 的 `modelChange()`，`app/Providers/AppServiceProvider.php` | 已有数据可复用，但缺中文字段、差异筛选、单位转换和主对象归属 |
| 原生 SQL / Query Builder 主要记录表名与操作 | `app/Providers/AppServiceProvider.php` | 批量更新、外部订阅源等不能自动得到逐个对象的真实差异 |
| 专用快照主要覆盖配置文件、主题和倍率 | `app/Services/SecurityAuditSnapshot.php` | 不能作为全部后台业务的统一采集机制 |
| 请求结果主要依据 HTTP 状态，只有节点管理部分接口额外记录响应 | `app/Services/SecurityAuditService.php` 的 `run()` | HTTP 200 中的业务失败、部分完成、无变化和预览结果不能可靠区分 |
| 队列有请求关联，但缺少业务对象及执行阶段详情 | `app/Services/SecurityAuditQueue.php` | “任务提交成功”不能说明向谁发送、实际执行了多少项、哪些失败 |
| 查看详情主要展示原始 JSON | `scripts/admin-security/audit.js` | 即使已经采到数据，也难直接看懂实际操作内容 |
| 正文、密钥及大字段存在脱敏和长度限制 | `app/Services/SecurityAuditService.php` 的 `redact()` | 无法直接依赖请求原文实现详细记录；必须设计业务字段策略及分段存储 |

调查还发现部分动作名称不够准确，例如用户 `ban` 接口实际执行停用，当前描述却是“批量停用或启用”；订单 `update` 实际修改佣金状态；Vless 节点 `update` 实际修改显示状态。这些应依据实际代码分支重新定义。

## 4. 统一记录结构与规则

### 4.1 业务详情

在新记录的签名载荷内新增版本化业务详情，不改写历史载荷。建议字段如下：

| 信息 | 拟记录内容 |
| --- | --- |
| 功能 | 模块、稳定动作代码、中文功能名称、操作类型 |
| 操作者 | 操作者 ID、当时的账号标识和角色快照、入口渠道；不依赖日后查询当前身份 |
| 主对象 | 对象类型、真实主键或订单号、协议类型、当时的名称；新增记录使用实际创建 ID |
| 字段变更 | 字段代码、中文名称、原始业务单位、中文显示单位、修改前与修改后；秘密字段只有是否修改 |
| 执行范围 | 选定对象、筛选条件、实际匹配对象、预览或正式执行标记 |
| 关联影响 | 订阅同步、关联删除、会话撤销、缓存清理等实际发生的效果及对象数量 |
| 结果 | 阶段、业务状态、修改 / 无变化 / 跳过 / 失败数量、安全处理后的原因 |
| 关联 | 请求 ID、任务 ID、任务执行次数、明细分段编号、对应审计序号 |

新载荷建议保留现有外层兼容格式，在 `details.business` 内使用独立版本号。采集器、中文描述、详情接口和导出共同遵守该结构。

### 4.2 变化与结果的判定

1. 比较实际保存前后的业务值，不把提交参数直接当作保存结果。排除 `updated_at` 等系统噪声；规范金额分、流量字节、日期时区、布尔值、枚举、权限组和套餐名称。
2. 新增、修改、复制、切换状态分别标注；没有实际业务变化时记“提交成功，未改变业务内容”。删除保留删除前快照；节点 ID 修改记录旧 ID → 新 ID。
3. 结果由各业务适配器根据返回值和实际执行情况判定，不能只看 HTTP 状态。预览只描述预览；失败、拒绝、部分完成、无变化分别展示。
4. SQL 变更与成功审计沿用事务一致性。回滚后不展示已成功修改；失败记录区分“尝试修改”与“已生效”。进程中断留下执行意图时显示“结果未确认”，不能推断成功。
5. 文件、Redis、第三方请求和邮件效果按真实执行阶段记录，不能因数据库回滚而宣称这些效果也已撤回。
6. 队列区分已提交、开始执行、完成、失败、重试和权限失效停止。邮件任务执行完成最多说明发送服务接受；没有送达证据时不写“用户已收到”。
7. 同一请求可能包含主对象和关联对象，保留所有实际变化，再按所属业务整理展示。不能只选第一条模型变化，也不能按某个时间范围推断全部变化属于本次操作。

### 4.3 敏感内容与历史兼容

- 密码、订阅令牌、UUID、支付密钥、私钥、恢复码、会话凭据不保存明文；在脱敏前判断是否真的改变，仅持久化“已修改 / 已重置”。中文概述也必须从脱敏后的业务详情生成，避免概述泄露秘密。
- 字段按业务白名单提取。不能通过移除现有脱敏规则、记录所有 SQL 绑定或复制整个接口响应来补细节。订阅 URL 等混合字段要遮蔽凭据部分。
- 公告和知识库默认记录标题、分类、显示状态、正文是否变化、长度及摘要；若采用正文差异，按字段策略处理后以纯文本展示。任意自由文本无法保证自动识别全部敏感内容。
- 工单和邮件默认记录工单 / 收件对象、主题、回复记录 ID、正文是否变化及长度。若“详细内容”明确包含回复或邮件全文，实施时将其作为单独的受控内容策略，限定审计查看和导出权限，不能仅放宽通用脱敏。
- 大批量对象分段写入，每段有明细和关联编号；列表可以收起，存储不能静默丢弃超出 1000 项的对象。长正文采用明确的摘要或分段策略，并在界面说明保留范围。
- 历史记录不 UPDATE、不重签名。有可靠旧快照时可生成中文展示；已经脱敏、截断或从未采集的内容显示“历史记录未保留”，无法补回。

## 5. 实现阶段

### 阶段一：编写实际功能覆盖清单

以后台页面按钮、注册路由、控制器分支和服务实际行为建立对应清单；不能以接口数量替代实际功能覆盖率。

每项填写：入口、功能、操作类型、目标定位字段、采集方式、敏感字段、成功与失败条件、批量或异步行为、验收场景。包含同一接口中的预览 / 执行、新增 / 编辑分支，以及管理员登录、自身安全、旧 staff、Telegram 和队列入口。

输出一份可用于开发及验收的功能矩阵，后续每接入一项更新状态，所有现有功能均应有明确记录策略。

### 阶段二：实现统一详情采集与中文格式化

主要涉及 `SecurityAuditService`、`SecurityAuditDescription`、`SecurityAuditSnapshot`，并新增业务动作定义及字段格式化组件。

实现版本化详情、目标快照、模型字段差异、中文单位与枚举、业务结果钩子、明确的无变化状态、分段记录及安全字段策略。保留底层意图 / 变化 / 完成记录和完整性机制。

Eloquent 用通用差异采集；其他写入在拥有业务上下文的控制器或服务中显式报告。批量 Query Builder 更新采用限定范围内的真实前后值或服务实际逐项结果，不做全表前后扫描。必要时使用事务与锁避免并发覆盖和错误归因。

先接通用户编辑、订单支付、单节点编辑和批量节点操作作为纵向验证，验证统一结构足以表达四类典型操作后，再铺开全功能。

### 阶段三：完整接入后台业务

| 模块 | 必须补充的业务内容 |
| --- | --- |
| 用户与管理员身份 | 资料、余额 / 佣金、流量、期限、套餐、限速、设备数、邀请关系、身份、停用、订阅重置 / 撤销 / 主订阅切换、Telegram 解绑、删除关联影响、清理扫描与实际删除、邮件目标 |
| 订单 | 订单号、用户、套餐、金额、佣金状态；分配、取消、支付确认、补单；支付或补单引起的订阅开通与其他实际关联变化 |
| 节点、权限组、路由、动态倍率 | 全部协议的新增 / 编辑 / 复制 / 删除 / 显示 / 排序；协议与 ID 联合定位；批量地址、名称、端口、TLS、协议设置和倍率逐项结果；权限组、路由、倍率规则与策略、绑定前后值 |
| 系统、支付、主题、签到娱乐 | 实际生效的配置字段、启停状态、支付驱动与主题名称；文件和模型差异；空密钥忽略、规范化配置、自定义 HTML / 脚本的内容处理策略 |
| 套餐、优惠券、礼品卡 | 名称、价格、配额、期限、适用范围、数量、状态；套餐强制同步用户的真实影响；批量生成的对象及数量，兑换凭据不明文记录 |
| 公告、知识库、工单 | 新增 / 编辑 / 删除 / 显示 / 排序、标题与分类；工单查看 / 回复 / 关闭，正文处理策略及通知结果；Telegram 回复使用明确的工单动作，不能只写 webhook |
| 外部订阅源 | 源 ID、名称、归属组、启用状态、脱敏 URL；新增 / 删除 / 刷新 / 试运行；实际节点变更及抓取失败原因，识别 HTTP 200 中的 `ok=false` |
| 风控、溯源、清洗网关 | 查询条件、目标用户 / 订阅 / IP / UA、阻断范围、理由、期限、状态前后、解除和处理结果；敏感信息揭示操作本身留痕 |
| 倒卖商 | 账号 / 店铺、审核状态与原因、模板、支付方式配置、密码重置、相关订单与配置变更 |
| 查询、统计、系统状态、导出 | 查看对象或筛选范围、实际返回 / 导出数量、任务或分页状态；不复制整库数据作为查询审计 |
| 登录、自身安全、审计自身 | 登录及二步验证阶段与结果、密码修改、会话撤销、退出、身份授权拒绝；审计查询 / 导出 / 校验 / 归档的范围及结果 |

实施顺序：用户 / 订单 / 节点及倍率 → 设置 / 支付 / 主题 → 套餐及内容业务 → 外部源 / 风控 / 倒卖商 / 其余入口。此顺序用于降低接入风险，不表示后续模块可省略。

### 阶段四：补齐批量与异步执行

复用现有节点批量服务的节点列表、前后值和跳过原因；为套餐批量同步、用户批量停用 / 删除、外部源替换等补充实际对象明细。汇总和各明细状态必须一致，预览与确认执行分开。

在 `SecurityAuditQueue` 和相关任务中传递业务动作、目标上下文、请求 / 任务关联与执行次数，继续执行前权限复核。按任务实际结果记录，避免因为任务没有抛异常就认为业务全部成功。

前端“全部刷新外部源”会发起多个请求，关联展示需要批次标识；每个请求仍保留独立结果。批量邮件任务按业务批次关联，收件目标不能依赖任务执行时重新查询当前筛选结果来猜测。

### 阶段五：实现中文审计详情界面与查询

主要涉及 `scripts/admin-security/audit.js`、`SecurityController` 和构建脚本生成的管理员资源。

1. 列表显示中文业务概述和实际结果；新增业务视图按请求或批次关联展示，原始逐条记录仍可访问。
2. 详情展示操作者、对象、动作、中文字段对照、关联影响、批量逐项结果、失败 / 跳过原因与任务时间线；提供原始证据入口。
3. 支持模块、动作、对象、字段、管理员、时间、结果筛选，以及请求 / 任务关联查询。详情内容以文本安全渲染。
4. 保留现有原始 JSONL 导出用于校验，可另提供与界面一致的业务导出。业务导出标明对应原始记录序号，不冒充原始签名载荷。
5. 先使用现有表和签名载荷实现。依据真实数据量验证查询成本；需要索引时建立可重建的查询投影，原始审计仍是证据来源，索引不参与改写旧链。
6. 重新生成管理员资源及清单，按现有角色隔离和构建校验流程验证。详细审计继续遵守现有安全审计查看权限。

### 阶段六：验收与发布准备

| 验收场景 | 必须达到的结果 |
| --- | --- |
| 实际功能覆盖 | 阶段一清单每项均有记录策略与验收证据；同接口不同操作分支可区分 |
| 修改与无变化 | 只展示真实字段差异，单位准确；重复提交同值不制造修改记录 |
| 新增、复制、删除 | 对象 ID 与名称准确，复制关联来源，删除后仍可读快照和关联影响 |
| 事务失败 | SQL 回滚后不显示成功变更；已发生的外部效果单独说明 |
| 批量与并发 | 完整明细不被尺寸限制丢弃；汇总一致；不把其他请求创建或修改的对象归到本操作 |
| 异步任务 | 提交与执行明确分开；重试、失败、角色撤销及业务返回失败可追踪 |
| 内容与秘密 | 密钥、凭据不进入概述 / 详情 / 导出；正文处理按策略，秘密变更仍能审计 |
| 历史与完整性 | 新旧记录均可读；原始历史载荷不改变；完整性校验及禁止修改 / 删除仍有效 |
| 页面与权限 | 中文概述与详情一致；请求 / 任务关联、筛选、导出有效；五角色权限不扩大 |
| 数据库与性能 | SQLite 及 MySQL / MariaDB 所需路径验证；批量记录、查询及投影可重建性能符合实际数据规模 |

以现有 `tests/Feature/AdminSecurityTest.php`、相关业务测试和 `scripts/tests/admin-security.test.cjs` 为基础补充有实际业务断言的测试，浏览器检查使用代表性详细记录及批量 / 队列场景。通过管理员构建校验后整理部署说明、产物和验收结果。

## 6. 工作量判断与交付边界

这是涉及多个模块的中等到较大改造，不能作为单次中文文案补丁完成。通用模型差异和页面展示可较快复用现有能力；主要工作量来自实际业务动作映射、原生批量写入、外部效果、正文策略和异步任务接入。
